# 漏洞判定规则详解

本文件定义补天SRC漏洞报告的三级判定规则体系：不符(F)、保留(R)、属实(T)。

---

## 一、判定为"不符"的规则 (F-01 ~ F-04)

判定为"不符"的漏洞报告存在根本性缺陷，不满足漏洞奖励计划的最低要求。

### F-01 — 资产所有权不符

**条件：** 漏洞URL对应的资产不在厂商专属SRC明确收录范围内。

**关键信号：**
1. URL/IP属于已知的不收范围（如 `svpn.example.com`）
2. Web应用指纹为第三方通用系统且非厂商定制（如 EasyConnect VPN）

**置信度：** 99%

### F-02 — 报告不符合基本要求

**条件：**
1. 仅有文字描述或理论猜测，无任何复现细节
2. 仅提供资产测绘、API端点列表，未证明任何实际漏洞或危害
3. 附件作为主要依据，漏洞详情栏目为空或内容不完整

**关键信号：**
1. 报告"漏洞详情"为空或仅一句话
2. "复现步骤"仅包含一个URL，无数据包、无响应对比、无利用证明
3. 报告主要内容是Hunter/FOFA扫描结果截图

**置信度：** 100%

### F-03 — 漏洞本身不成立或无危害

**条件：**
1. 页面显示功能错误（如Swagger UI显示"Failed to load API definition"），无实际利用可能
2. 报错信息不包含任何敏感数据（如服务器路径、代码堆栈、数据库结构等）

**关键信号：**
1. Swagger页面报错"Failed to load API definition"
2. 响应包仅包含通用错误信息，如"404 Not Found"、"Internal Server Error"

**置信度：** 95%

### F-04 — 漏洞类型明确不在奖励范围

**条件：** 属于企业SRC漏洞奖励计划公告的不予奖励的漏洞类型清单。

**具体子类：**

**信息泄露类：**
- 不涉及敏感信息的CORS配置错误
- 无意义的内存/日志/内网IP泄露
- 示例文件泄露
- 前端源码泄露

**功能缺陷类：**
- 地图Key及其他Key造成的资源不受限调用
- 虚假的前端绕过（如通过卡包绕过但功能无法使用）
- 上传PDF造成的XSS

**配置缺陷类：**
- Web安全配置缺陷或安全加固缺失（如缺少X-Frame-Options头）

**权限问题类：**
- 无意义的未授权接口访问（不涉及敏感信息、无法调用敏感接口）

**其他情况：**
- 无意义的并发问题（如点赞、收藏）

**关键信号：**
1. 报告标题直接包含"CORS"、"缺少X-Frame-Options"、"源码泄露"
2. 漏洞描述为可访问一个不返回数据的内部API路径或 `swagger.json`
3. 并发操作仅为用户可主动发起的点赞、关注等非利益功能

**置信度：** 98%

## 二、判定为"保留"的规则 (R-01 ~ R-04)

判定为"保留"的漏洞报告存在一定安全隐患，但缺乏直接、完整的危害利用证明，或属于低风险/边缘场景，需要进一步观察或组合利用。

### R-01 — 非敏感信息级泄露

**条件：**
1. 调试信息、phpinfo、.svn文件泄露、GitHub上存活的测试服务器弱口令等
2. 少量经授权的公开个人信息泄露，如手机号、姓名
3. 提供了一般信息的logcat泄漏

**关键信号：**
1. 泄露内容为路径、版本号、技术栈名称
2. 个人信息数量极少（<10），且无法获取身份证、住址等高敏感字段
3. 声称泄露但无法提供任何敏感数据截图

**置信度：** 85%

### R-02 — 漏洞利用门槛高或无法独立造成危害

**条件：**
1. 需交互才能利用的漏洞（如反射型XSS）
2. 无法利用的漏洞（如无意义的目录遍历、Self-XSS、DOM型XSS）
3. SSRF仅能访问DNSLog，无法获取内网信息或凭证
4. 攻击链不完整，比如发现了速率限制缺失但验证码策略弱，无法独立完成攻击

**关键信号：**
1. 反射型XSS报告要求攻击者点击构造好的链接
2. SSRF报告中唯一的利用结果是请求了dnslog.cn
3. 报告引言或总结部分写道："该漏洞/攻击链尚不完整，需进一步组合利用"

**置信度：** 90%

### R-03 — 系统/服务本身的暴露但未深入利用

**条件：**
1. 系统接口泄露：Webpack打包文件、Swagger接口文档等暴露，但无法证明系统可被进一步攻击
2. 未授权访问：Zookeeper、Memcache、Redis等未授权访问，但无法证明获取了有价值的数据
3. 需要进一步利用：GitLab开放注册可能导致信息泄露，但未证明存在高价值数据或危害

**关键信号：**
1. 报告核心是利用 `/swagger-ui.html` 或 `/webpack/` 路径的发现
2. 提供了系统/服务的管理界面截图，但未展示任何可读取的敏感数据
3. 允许任意用户注册或登录，但无法访问后台或他人数据

**置信度：** 85%

### R-04 — 利用价值低的逻辑缺陷

**条件：**
1. 登出后Token/Session未失效，但该Token无敏感权限
2. 登录接口已实施账号/IP限制，仅缺少验证码校验
3. 扫描结果中常见的、利用难度极高的报告，如仅指出"站点使用HTTP协议"

**关键信号：**
1. 报告声称"会话未失效"，但后续API请求返回的都是"未登录"或空数据
2. 报告核心发现是"HTTP而非HTTPS"
3. 爆破或枚举行为在少量尝试后即被规则拦截

**置信度：** 80%

## 三、判定为"属实"的规则 (T-01 ~ T-02)

### T-01 — 完整攻击链或直接利用危害

**条件：** 报告能从一个未经认证的入口点，通过一系列组合漏洞，清晰、完整地证明对业务或数据造成实质性损害的过程，而非理论猜测。

**关键信号：**
1. 漏洞危害：如越权查看/修改他人订单、控制用户账户、获取大量用户隐私数据等
2. 攻击链清晰：`[A漏洞] → [B漏洞] → [C危害]`，每一步都有完整的请求/响应包作为证据
3. 报告明确展示了漏洞的实际影响，如修改数据后的数据库截图（而非页面提示）

**置信度：** 99%

### T-02 — 未授权访问高敏感数据

**条件：** 未经任何认证，能够直接获取、列举或下载包含大量用户的核心敏感信息（如身份证号、银行账号、密码哈希、详细交易记录）或企业核心商业机密数据。

**关键信号：**
1. URL/接口直接返回包含大量用户信息的JSON/CSV数据
2. 证明具备批量爬取数据能力（如修改ID参数遍历）

**置信度：** 99%

## 严重等级判定参考

| 漏洞类型 | 严重 | 高危 | 中危 | 低危 |
|---------|------|------|------|------|
| 信息泄露 | 10W+条/核心数据 | 1W+条/员工信息 | 500-1W条/一般信息 | 少量非敏感 |
| 未授权访问 | 核心管理后台 | 内部系统/API | 测试环境 | 无数据仅暴露 |
| RCE | 无条件RCE | 有条件RCE | — | — |
| SQL注入 | 核心DB | 重要DB | 非核心DB | 难利用 |
| SSRF | — | 可访问内网服务 | 有回显但有限 | 无回显 |
| XSS | — | 核心存储XSS | 一般存储XSS | 反射XSS |

## 401/403 处理规则

- **401/403 响应 ≠ 存在未授权漏洞**
- 不能以返回401/403的端点声称"未授权访问"
- 除非证明存在：认证绕过方式、响应体实际含敏感数据、或不同路径绕过
- **公开数据接口**（开放API目录、数据平台、天气/股票API等）不算未授权
- **SPA catch-all 页面**（前端框架的所有路由都返回200 + index.html）不算有效端点
